## 4. 新问题 H25–H30

这里的 P0 延续上轮定义：错误执行、未确认的持久动作、恢复原件丢失或虚假成功。复现均使用合成输入、临时目录或外部动作桩，没有在生产执行安装、卸载或恢复。

<a id="h25"></a>
### H25 · P0：临时公开入口丢失子进程失败码

位置：[xtun.sh](../xtun.sh) 的 `bootstrap_run_temp_bundle`。`if ! env …; then status=$?` 取得的是逻辑取反后的成功状态，子进程失败时外层仍 `exit 0`。

隔离方法：提取该函数，令 `env()` 返回 23、`rm()` 为无副作用桩，再调用函数。实测外层退出码为 **0**。现有临时归档入口测试主要验证帮助成功、临时目录清理和回退入口，没有钉住此失败传播。

处理：W01-R 保留真实退出码并完成清理，覆盖 0/1/2/130/143；W08.2 另处理写动作下载失败后静默使用旧 bundle 的身份问题。不能用一条内部 dispatch 测试替代公开单文件入口。

<a id="h26"></a>
### H26 · P0：安装与卸载在确认前进入修改边界

位置：[安装入口](../lib/cli/install.sh) 的 `prepare_install_command`、[卸载入口](../lib/cli/core.sh) 的 `uninstall_cmd`。两者在任务/输入确认前调用 `start_backup_session`；该函数调用 `begin_mutation`、创建锁和备份目录，并开启后续操作日志。

隔离方法：用记录调用的桩替代 `start_backup_session`，分别在任务选择处取消安装、在卸载确认处回答 n。两条路径均先输出 `mutation boundary entered`，随后才取消。这是调用顺序证据，不是声称本轮在生产留下了备份。

处理：W01-R 移动共用执行边界，W05-R 联合复验完整向导。确认前允许读取和明确的独立草稿动作，不应因打开向导、取消或 EOF 自动创建锁/日志/备份。锁后重新核对预览依据；发生实质变化时终止旧确认并要求重新预览。

<a id="h27"></a>
### H27 · P0：首次不存在的路径可被二次备份改写

位置：[备份层](../lib/base/env.sh) 的 `backup_path`。幂等检查只看快照路径是否存在；首次目标不存在时仅写 manifest，没有快照，后续目标被创建后又会备份并追加 `existed=1`。恢复优先使用快照，manifest 查询又取最后一条记录。

临时目录复现：不存在 → `backup_path` → 写入候选文件 → 再次 `backup_path` → `restore_generation_path`。实际得到：

```text
original-existed-after-second-backup: 1
restore-result: restored
resource-exists-after-recovery: yes
```

正确结果应保留首次 `existed=0`，回退删除本次创建的文件。原 `run_backup_first_snapshot_case` 覆盖了“原本存在后修改”的重复备份和一次不存在记录，未覆盖这个组合。

处理：W02-R 以首次登记为准判断是否已备份，存在/不存在同样不可重写；缺失或损坏的证据不能解释成“原本不存在”。

<a id="h28"></a>
### H28 · P0：恢复元数据失败被忽略，未完成清单遗漏路径

位置：[备份层](../lib/base/env.sh) 的 `backup_manifest_init/record`、[同代恢复层](../lib/base/generation.sh) 的 `mark_pending_operation`、`begin_generation`、`generation_add_paths`。

- 将临时备份目录下的 `manifest.tsv` 设为目录，真实 `backup_path` 写清单失败，仍退出 0。源码也将 manifest 写入错误用 `|| true` 吞掉。
- `mark_pending_operation` 多条写入失败分支只警告并返回 0，因此当前实现允许没有可用未完成标记时继续执行。
- 升级/安装在 `begin_generation` 已落标记之后才追加核心、资源或 bundle 路径。按同样调用顺序复现，标记缺少 `/synthetic/xray-bin` 与 `/synthetic/xray-assets`，尽管内存恢复列表已有它们。

处理：W02-R 使备份登记失败明确返回；W04-R 在修改前持久化完整路径与服务清单，校验失败停止。普通过程日志与必需恢复证据采用不同失败策略；新增路径不能只更新内存。强杀/掉电没有 INT/TERM trap，不能把信号测试写成掉电恢复通过。

<a id="h29"></a>
### H29 · P0：恢复遗漏原先 inactive 的服务

位置：[同代恢复层](../lib/base/generation.sh) 的 `recover_generation`。它只重启原先 active 的服务，其余直接跳过；没有确保被本次动作启动的服务重新停止。

隔离方法：记录 `xray.service=inactive`，当前服务状态桩返回 active，调用恢复；实际结果为：

```text
recovery=restored-verified, service=active, original=inactive
```

这是恢复判定反例，没有实际重启本机服务。处理：W04-R 对原先 active、inactive、未安装等情形分别保存和核对所需状态；本次修改了启用状态时一并恢复。必要步骤包括 unit 重载失败时，不能只警告后继续报告完整恢复。仅检查“最后服务是否 active”不满足回到操作前状态的契约。

<a id="h30"></a>
### H30 · P1：H3 自动启用仍与目标默认冲突

位置：[能力判定](../lib/ui/core.sh) 的 `h3_disabled_reason/h3_enabled`、[输出](../lib/ui/output.sh) 与 [nginx 生成器](../lib/generators.sh)。当前只以 nginx 模块和 `CERT_MODE=existing/acme-dns-cf` 判断启用，没有持久的显式 H3 意图，也没有用完整证书信任结果决定能力。

隔离方法：只令 `nginx_v3_capable()` 成功、设置 `CERT_MODE=existing`，不提供任何启用请求或证书验证结果；`h3_enabled` 已返回成功。existing 只是来源，可能装入 Origin CA 或自签证书，不能证明直连客户端信任。

处理：W09.1 提前落实显式意图、证书用途和 UDP 归属条件，保留旧已配置 H3 的迁移记录。当前帮助把 H3 列在默认关闭项中，属于待修文案；本轮只在文档说明现状，不通过改文档伪装代码已修复。

### 5.1 共享 HAProxy 的卸载收尾

[W05](REPORT-2026-09-14-W05.md) 和 [W06](REPORT-2026-09-14-W06.md) 均记录：卸载删除配置后按保守策略保留 haproxy 运行，reload 失败，进程继续以旧内存配置占 TCP/443。当前 `uninstall_cmd` 对保留服务的 reload 仍使用 `|| true`。
