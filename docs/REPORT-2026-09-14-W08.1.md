## 2. W08.1 交付

### 2.1 候选校验的每一步都自己传失败（H16）

`lib/base/versions.sh` 的 `xray_validate_candidate_commands` 在 install / upgrade / 菜单三条路径里都被 `if !` 或 `||` 调用，调用方豁免掉的 errexit 会一路传进来——原来「靠 `set -e` 兜底」的断言在这种上下文里会静默通过：字段空的假核心、恒返回 0 的 `run -test`、随便打印的 vlessenc 都能过。

- 每一步改成显式 `|| return 1`：参数非空、tag 形如 `vX.Y.Z`、二进制可执行、`version` 首行与期望版本一致、`x25519`、`vlessenc`、两个候选配置写入与 `-test`、清理。
- 新增 `xray_validate_x25519_output`：三个字段（`PrivateKey:` / `Password (PublicKey):` / `Hash32:`）必须都在、都带值，且值符合 base64/base64url 字符集；空值或整行缺失都算候选无效。
- vlessenc 解析出的 `decryption` / `encryption` 必须都是 `mlkem768x25519plus.*` 且不相等。
- **坏配置反向对照：** 在同一个操作目录里再写一份非法 JSON 交给候选执行 `run -test`，候选必须拒绝它。少了这一步，一个「好配置返回 0、坏配置也返回 0」的假核心能通过其余全部检查——这正是 H16 描述的绕过。
- `xray_validate_candidate_archive` 补上 target 目录与 `XRAY_SELECTED_TAG` 的存在性检查。

### 2.2 候选配置只在本次操作自己的目录里（H16）

- 固定名字 `/tmp/xtun-xray-server.json` / `/tmp/xtun-xray-client.json` 删除，改用 `mktemp -d "${TMPDIR:-/tmp}/xtun-xray-candidate.XXXXXX"`；函数体改为子 shell 并在 `EXIT` 上清理，成功、校验失败、中途被中断三种退场都不留半份临时配置，也不会和同机另一次操作撞名（tests 里钉了「两次校验目录不同 + 跑完目录为空 + 固定名字不出现」）。

### 2.3 版本上下文属于「这一次动作」（H15）

- `XRAY_CONTEXT_REQUEST` / `XRAY_CONTEXT_ARCH` 记录上下文是替哪个请求、哪个架构解析的；`xray_prepare_release_context` 成功时一并写入，`xray_reset_release_context` 一并清掉。
- 新增 `xray_ensure_release_context <request> <arch>`：请求与架构都对得上才复用已锁定的选择（同一次动作里不重复打网络），否则重新解析；新增 `xray_release_version_context` 表示「动作结束，释放」。
- `lib/install.sh` 的 `install_xray` 不再只判断「上下文是否 ready」，一律走 `xray_ensure_release_context "${XRAY_VERSION_REQUEST}" "${arch}"`：菜单里先解析过 `v26.9.9`、下一次动作要 `v26.10.1` 时会重新解析，不会沿用旧 selected。
- `lib/cli/core.sh` 的 `run_cli_command`（命令与菜单动作的共同入口）在 dispatch 前先释放一次、dispatch 后与锁一起释放，连续动作不会互相污染。
- 顺带修掉 `install_xray` 里两处不受守卫的退出：`detect_xray_arch` 失败与 `mktemp -d` 失败现在按 `return 1` 返回（原来 `exit 1` 会直接结束进程，跳过调用方的同代回退出口），并且解析失败时也会清掉已经建好的临时目录。

### 2.4 回归用例（`tests/cases_versions.sh` 新增 5 条）

| 用例 | 钉住的行为 |
| --- | --- |
| `run_candidate_validation_call_context_case` | 真核心（含 errexit 被豁免的上下文）通过；x25519 空值、vlessenc 非 ML-KEM 对、version 不符、`run -test` 恒 0 四种假核心都被拒 |
| `run_candidate_work_dir_case` | 每次校验用新的唯一目录、跑完不留残渣、不出现固定 `/tmp` 名字；失败路径同样清干净 |
| `run_release_version_context_scope_case` | 同请求同架构复用不重复打网络；换请求、换架构重新解析；上游出现新版本后回到 latest 重新解析；释放后从头解析 |
| `run_install_xray_requested_version_case` | 同一个进程里连续两次动作按各自请求下载（第二次不会拿到第一次的 URL） |
| `run_version_context_action_boundary_case` | 命令入口在动作结束后释放上下文 |

既有的 `run_xray_candidate_commands_case` 的假核心同步补上「拒绝坏配置」的行为——它原来钉的是弱一层的契约。

## 5. 遗留与后续输入

- 同版本可信身份比较、noop 与 `upgrade --reinstall` 属 **W08.3**；下载/解压/setcap/geo 写入/服务重启的失败窗口按 W04 同代边界处理，也属 W08.3；bundle/入口 ref 与完整持久安装清单属 **W08.2**。本轮没有把 H15 的「同版本仍重装」当作已修。
- 候选校验用的仍是两个最小合成配置（dokodemo/freedom、socks/freedom）。真实五类节点配置在安装 finalize 阶段由 `validate_configs` 用刚装上的核心跑 `-test`，失败会按 W04 的同代边界把二进制一起退回；这一点的实机证据在 W04 报告。要让候选阶段就跑真实配置，需要先有完整 state 上下文，留到 W08.2/W09。
- 实机未覆盖：解压失败、setcap 失败、geo 写入失败的注入（属 W08.3 的失败窗口清单）。
