## 7. 三个与文档不符的现实问题（本次审计新增）

### 7.1 R1：未提交的私有 DSH 网关改动（`lib/generators.sh:736`）

```diff
     use_backend be_xhttp_cdn if { req.ssl_sni -i ${XHTTP_DOMAIN} }
+    use_backend be_dsh_gateway if { req.ssl_sni -i dsh.564672.xyz }
```

- 现场 `/etc/haproxy/haproxy.cfg` 里确实有 `backend be_dsh_gateway`（`server 127.0.0.1:3443`，指向正在运行的 DSH 网关），它位于 `# >>> xtun-user:haproxy-extra >>>` 用户块内，会被生成器保留。
- 但**仓库代码里没有任何地方定义这个后端**。用户在**没有该用户块的机器**（全新安装、CI、其它 VPS）上重新生成配置时，`use_backend` 会引用未定义后端，`haproxy -c` 失败 → 安装/应用配置失败。
- 该改动与 `haproxy.cfg` 的修改时间同为 `2026-09-19 02:34`，是最近一次本地定制，**未提交、未进文档、未进计划**。
- 测试不会拦住它：`cases_nginx_net.sh`、`cases_output.sh` 只断言 `be_xhttp_cdn`，不跑真实 `haproxy -c`。

> 结论：如果这是长期需要的路由，正确做法是把它写进用户块（随用户块保留），而不是硬编码进发布代码；如果只是本机临时需求，应把这一行从工作区撤掉，避免将来误提交。

### 7.3 R2：测试 VPS 的 nginx 已经挂了两天

- `nginx -t` 失败：`unknown directive "http2" in /etc/nginx/conf.d/xtun.conf:8`。
- 安装的 nginx 是 **1.22.1**（dpkg `1.22.1-9+deb12u10`），而独立 `http2 on;` 指令要 **1.25.1+**。
- 根因（**推断**，与文档记载吻合）：[TEST-VPS-RUNBOOK.md:51](TEST-VPS-RUNBOOK.md) 自己记过"测试 VPS 实际 nginx 1.30.1、dpkg 记录 1.22.1"。配置是按 ≥1.25.1 生成的（生成器 `nginx_version_at_least 1.25.1` 判断通过，见 [generators.sh:551](../lib/generators.sh)），而 **2026-09-18 16:42 的 apt 升级**（`/var/log/apt/history.log`：nginx u9→u10）恰好与 nginx 开始失败同一分钟。最合理的解释是人工放置的 1.30.1 二进制被包管理版本覆盖，配置与新二进制不匹配 → 服务起不来，`systemctl` 一直在 auto-restart（当天失败计数 7000+）。已确认的事实只有"当前 1.22.1 + `http2 on;` = 起不来"。
- 影响面：该 VPS 的 xtun 安装本身就是**测试夹具现场**（state 里 `SERVER_IP=127.0.0.1`、`XHTTP_DOMAIN=recovery.example.test`，是 9-15 恢复/验收测试留下的），所以这不是真实用户中断；但 `be_xhttp_cdn → 127.0.0.1:8443` 这条路径确实不可用，且与 `PLAN.md` 第 7 行"服务状态与最终快照一致"的记载矛盾。
- 修复方向（未执行）：要么把托管配置回到 `listen … ssl http2;` 旧语法（对应 nginx 1.22），要么恢复 ≥1.25.1 的 nginx；两者都涉及改配置/换二进制，本次审计按只读原则未动。
