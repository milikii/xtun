## 2. W04 交付

### 2.1 同代提交与恢复层（`lib/base/generation.sh`，新增 385 行）

- 一次托管变更 = 一个「代」：`begin_generation <label> <include-tls> <units…>` 在动任何文件之前记下这一代要碰的路径清单和服务当时的 `ActiveState`；`begin_generation_xray_only` 是只改 UUID/客户端设置时不带 haproxy/nginx 的窄代，回退清单越小越好。
- 路径清单覆盖托管配置（xray / haproxy / nginx 含 limits drop-in / WARP 规则 / logrotate / 回退站点目录）、TLS 证书与密钥、acme reload helper、接管的 nginx 主配置，以及 `state`、节点输出和 PNG 目录——state/output/PNG 现在是这一代的交付物，配置换了它们没跟上就跟着回退（H14）。
- `restore_generation_path` 用快照 + `manifest.tsv` 区分四种结果：`restored`（有快照，还原）、`deleted`（清单写明原本不存在，删除本次产物）、`untouched`（本次根本没碰，不需要动作）、`unconfirmed`（清单说动过但快照没了——缺证据不能自动解释成「以前不存在」，保留现状并列入未恢复）；后两者都不算「已恢复」。
- `recover_generation` 顺序固定：逐路径还原 → `daemon-reload` → 对操作前处于 active 的服务做重启核对；全部有证据可恢复才 `restored-verified`，否则 `recovery-failed`。
- `generation_failed` 是统一失败出口：两种结果分开报告且**都**返回非零——`restored-verified` 说「本次变更没有生效」，`recovery-failed` 逐个列出仍未回到操作前状态的组件（如 `xray.service`）并保留现场目录；任何路径上都不再出现「失败却报成功」。
- `generation_commit` 只在成功后调用 `finish_backup_session`：失败/回退过的动作不消耗备份保留名额（H13/D11）。

### 2.2 未完成操作清单（掉电 / 中断现场）

- 新增 `PENDING_OP_FILE`（默认 `/var/lib/xtun/pending-op.tsv`，可被 `XTUN_PENDING_OP_FILE` 覆盖）：`begin_generation` 在动作开始时原子写入 label、op_id、开始时间、涉及服务与路径。
- 提交成功清除；`recovery-failed` 保留（清单就是现场，下次维护动作才有入口）；写不进去只警告，不影响主流程。
- 查看入口只报告、不自行恢复（D12）：`show_dashboard_brief` / `show_dashboard` 在有清单时显示「上次动作：未完成：<label>（开始于 …，现场：…）」，完整面板另给处理方式（`xtun apply-config` 或按备份目录手工恢复）。

### 2.3 中断边界（D04）

- `install_mutation_traps` 在 `begin_mutation` 时安装 INT/TERM 处理器；`mutation_interrupt_handler` 先走 `generation_recover_on_interrupt` 回退并核对服务，再释放脚本锁，退出码按信号取 130（INT）/ 143（TERM）——变更中途 Ctrl-C / 断电不再留下半套系统。

### 2.4 成功以实际状态为准（H11）

- `restart_service_verified`：重启命令返回 0 不算成功，`service_active_state` 连续两次看到 `active` 才算（`Restart=always` 的核心在崩溃重启间隙里也会短暂 active）；结果字符串写进 `SERVICE_ACTION_RESULTS`，面板/报告可直接引用。
- `reload_or_restart_service`、`restart_service_if_present`（`restart` 命令）全部改走该核对；`repair-perms` 等维护动作同样不能把「尝试过」当「已恢复」。
- `service_exists` 归一化 unit 名（补充 `.service`）：以前拿 `haproxy` 简写去查 `/lib/systemd/system/haproxy` 一定查不到，会把装着的服务判成 not-installed，重启核对跟着失败——这条在实机安装路径上真实触发过服务重载失败。

### 2.5 交付物与清理

- `write_link_qr_pngs` 改为 staging 整批语义：先在 `<QR_OUTPUT_DIR>.staging.XXXXXX` 里画完全部 PNG，全部成功才整目录换上去；失败或 qrencode 缺失时不留上一代旧图、也不留半套新图或暂存目录，整代回退（H14）。缺 qrencode 时明确报告「为避免留下上一代二维码已清空」。
- `xray_log_json` 的日志路径改用 `jq --arg` 传入：单引号里的 `${XRAY_LOG_DIR}` 不会展开，之前 JSON 里落的是字面量，xray 会因为找不到 access.log 直接起不来。
- 同值修改（含规范化与 `post_update` 之后的同值）是 noop：算清「改完和现在一不一样」之后才 `open_change_session`，不写文件、不重启服务、不开备份会话、不提示重新导入链接（`run_same_value_change_noop_case`）。

### 2.6 本轮修掉的具体缺陷（均有回归覆盖）

1. `tests/cases_change.sh` 的 `run_upgrade_command_case` 把回退中的 `systemctl daemon-reload` 当成重启计数，掩盖了「失败路径不该重启」的断言——改为断言 `systemctl_calls` 不含 `restart`。
2. `run_link_qr_png_case` 按新的 staging 整批语义重写：失败时旧图逐字节保留、目录下无 `.staging.*` 残留。
3. `install_abort_with_recovery` 缺 `return 1`：CLI 入口的 `if ! …; then install_abort_with_recovery …` 在 `|| status=$?` 豁免 errexit 的情况下不会中止，安装失败会继续往下走——函数补 `return 1`，三个失败分支跟着补 `return 1`；`run_install_flow_case` 重写为同代断言。
4. `xray_log_json` 日志路径字面量化（见 §2.5）；`tests/cases_output.sh` 增加 `.log.access` / `.log.error` 等于真实路径的断言。
5. `service_exists` 不认简写导致 `reload_or_restart_service haproxy` 报 not-installed、安装整体回退（见 §2.4）；新增用例 `run_service_unit_name_case`。

排查中的重要事实（后续工单可复用）：xray 的 unit 自带 `ExecStartPre=xray run -test …`，所以「假核心一律让 `-test` 失败」会连带把服务启动打死，注入故障要分清「配置校验被拒」和「服务起不来」；VPS 上 `service_active_state` 与实际服务状态是可靠的，真正的坑是 `service_exists` 的简写匹配和 `/root` 0700 让 xray 用户 exec 不到夹具。
