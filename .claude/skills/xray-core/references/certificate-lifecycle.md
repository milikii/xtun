# 证书生命周期：签发、部署、续期与生效

这是让 harness 按环境实施的标准流程，不是加载技能即运行的安装脚本。
签发会访问 CA/DNS，公有证书通常进入公开的证书透明度日志；变更前应确认域名、账户、权限和用户授权。
不得从对话索取 DNS API Token、ACME 账户私钥或证书私钥。

## 来源及版本

- Let's Encrypt [挑战类型](https://letsencrypt.org/docs/challenge-types/)；
  Certbot [使用手册](https://eff-certbot.readthedocs.io/en/stable/using.html)；
  Cloudflare [Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)。
  核查日期/范围见 [运维来源](operations-sources.yaml)。外部手册是滚动内容，操作前核对已安装工具版本。
- Xray [TLS 文档](../docs/stable/config/transports/tls.md) 与 v26.9.30
  [BuildCertificates / setupOcspTicker](../source/versions/v26.9.30/transport/internet/tls/config.go)。
  换版本需再查实现；其他进程的证书加载行为不能从 Xray 源码推断。

## 1. 先分配证书责任

| TLS 段 | 谁呈现证书 | 谁负责更新 |
|---|---|---|
| 客户端 → CDN | CDN 边缘 | 按 CDN 服务的证书管理策略 |
| CDN → 源站反代 | 源站反代 | 所选 CA/ACME 客户端及源站维护者 |
| CDN → Xray 直连回源 | Xray | 所选 CA/ACME 客户端及 Xray 加载机制 |
| 受控本机反代 → Xray 明文 | 不终止 TLS 的 Xray 无需这段证书 | 保障本机边界；跨公网另行设计保护 |

源站专用证书不必然被浏览器/普通 Xray 客户端信任。公网直连需求、CDN 回源需求和本地测试信任锚
分别设计；不为省事在客户端关闭验证，也不默认把根证书塞进 fullchain。

## 2. 选择能自动重复执行的挑战方式

- **DNS-01**：适合不开放 HTTP 验证端口、CDN 前置或泛域名的情况。选择实际 DNS 供应商支持的插件，
  确认传播等待、TXT 记录管理和失败清理。使用最小范围 Token；DNS API 权限与秘密路径不回传模型。
  可按 CA 文档评估验证记录委派，不随意改生产 DNS。
- **HTTP-01**：CA 通过 80 端口验证；需要域名解析、代理/重定向、WAF 和验证路径实际满足挑战。
  泛域名不能用此方式。已有站点优先评估正确 webroot，不为 standalone 模式随意停外来服务。
- 其他挑战或证书来源按其官方实现选择。手工交互验证不等于可自动续期；不要声称配置了计划任务就解决了认证。

建议复用环境已有且合适的 ACME 客户端。本文以 Certbot 说明流程，不自动安装第二套客户端，
不混用 Certbot 与 acme.sh 的目录、钩子、默认 CA 或状态文件。

## 3. 首次签发与部署

1. 检查系统时间、DNS 控制权、CA 账户及速率限制。先验证挑战路径和需要的插件，必要时使用 CA staging，
   **staging 证书不可作为公网可信证书交付**。
2. 在真实执行环境确认客户端版本和帮助文档，然后构造对应的签发命令。DNS Token 由用户直接放入私有凭据文件
   或受限秘密存储，不出现在 CLI 参数、聊天或 shell 跟踪日志中。
3. 将证书/私钥部署到使用进程可读取但其他用户不可读取的位置。需要服务组权限时最小化授予；
   不笼统把私钥改成 world-readable。确认父目录、软链接目标、容器挂载及服务实际 UID 都可访问。
4. 本地程序验证证书与私钥匹配、SAN、有效期及所需完整链，**只返回结论**。不要打印私钥或把它读给模型。
5. 若另行复制 ACME 输出，采用成对发布、可恢复的方式，避免进程在证书/私钥更新中间读到不匹配的组合。
   保存现有有效材料的私有备份，失败不破坏运行状态。
6. 对实际进程做配置检查，然后按该进程支持的方式加载证书。不能假设所有服务都支持 `reload`，
   不能默认发送一个未核实的信号；需要 restart 时说明中断及回退。
7. 用正确 SNI 检查网络端点实际呈现的证书，再验证 CDN 回源和代理数据链路。

配置文件指向新证书路径不证明进程已使用它，磁盘证书正确也不代表网络端点正确。

## 4. 建立续期闭环

对已存在、获准管理的 Certbot 环境，可按其实际配置验证续期路径：

```text
certbot renew --dry-run
certbot renew --deploy-hook /path/to/reviewed-deploy-hook
```

上面是命令形态，不要求操作者无条件执行两条。必须先审查 hook 内容和副作用；dry-run 的
hook 行为也受版本/选项影响，不能认为测试续期已经测试过部署 hook。

关键语义（官方 Certbot 手册）：

- `renew` 成功退出可以只是“没有证书需要续期”，不是本次已经换了证书。
- 只想在实际成功续期后部署，用 **deploy-hook**，不要以返回码 0 或普通 post-hook 代替这一条件。
- hook 负责把正确证书提供给正确进程，并做该进程的配置检查、加载/重启及必要验证；
  不把 Token 或私钥放进 hook 输出。全局 hook 要按证书身份筛选，不能每张证书都重启所有服务。
- 先检查发行版/安装方式已有 timer、cron 或调度器，再在明确授权后补缺；不要创建重复的续期任务。
- 记录任务身份、运行环境、插件/凭据路径、日志权限、告警接收者及失败重试方式。
  单次 dry-run 通过不能证明无人值守环境的 PATH、权限和凭据也正确。

完成标准是：**挑战可自动完成 → 新证书安全部署 → 进程实际加载 → 端点呈现正确证书 → 链路复验**。
分别监控磁盘证书与实际端点的剩余有效期。需要重启的服务应安排维护窗口；续期失败不要先删旧证书。

## 5. Xray 直接持有证书时的版本化注意事项

已收录 v26.9.30 的 `setupOcspTicker`：

- `oneTimeLoading` 会退出热重载逻辑。
- 热重载间隔基线为 3600 秒；非零 OCSP 配置会改变该间隔及行为。
- 文件路径必须存在且运行 UID 可读；仅内嵌证书内容不能靠替换磁盘文件完成这种重载。
- 读取证书/私钥失败的路径会退出该重载 goroutine；不能断言它总会自动重试恢复。

因此不要承诺“续期后立刻自动生效”，也不要为了缩短证书加载时间而无理由开启 OCSP。
核对版本、加载配置与日志分类，并通过网络端点确认。若由 Nginx/Caddy 等终止 TLS，
应查该进程的官方加载/自动管理机制，而不是继续套用 Xray 的重载规则。

## 6. 必须保留的未验证项

本指南没有替用户申请真实证书、创建 timer、更新 DNS 或重启服务。
只有在具体目标上实际执行后，才能记录其签发、续期、hook、进程加载和外部链路通过。
外部工具命令无法实时核实时，列为待核验步骤，不生成“已完成续期配置”的结论。
